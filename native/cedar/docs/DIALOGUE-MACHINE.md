# Bounded authored dialogue control runner

GPL-3.0-only adaptation of the authored control behavior in [NativeDialogueBody.js](http<LOCAL_REFERENCE>/NativeDialogueBody.js), by brynnb / New Yokosuka, pin `b0df7f2720a7eecabce2e610fdedec35bf1243e3`. No conflicting per-file notice was present. Complete GPL retained at `third_party/licenses/new-yokosuka-GPL3.txt`; provenance limitations in `ENGINE-BASIS-NEW-YOKOSUKA.md` apply. This is authored-reference compatibility, not proven recovered original-engine semantics. Imported predicate/selector modules, generated tables, actor/story data and original C examples are excluded.

`DialogueMachine` borrows an immutable routing slice of at most 16MiB and an explicit initial state/body offset, outer/group mode and opaque numeric identifier. Caller retains the slice through reset/destruction, synchronizes all calls and must not overwrite it through other aliases. No heap, IO, asset lookup, CPU emulation or hidden native-event execution exists. `decode_dialogue_body` supplies bounded instruction descriptors; unsupported or truncated commands stop at their byte without inventing a length.

## Actual control execution

`advance(budget)` accepts 1–4096 steps per call. It executes proven noops, unconditional/conditional relative branches, outer-to-message-group entry at the same cursor, saved call continuation60 and F9 local return, saved continuation64, and source-proven invoke operand0x10 bypass. The source uses one continuation60 slot, not an invented recursive call stack. Continuation64 is retained as metadata, not automatically used for an unproved return. Out-of-range positions stop; no loop runs beyond the explicit budget. A budget stop can retain preceding valid internal steps; it is not a transactional rewind of the entire call.

Conditional branches require an explicitly valid zero/nonzero predicate. Caller may supply one in resumed state or `supply_predicate` when no action is pending; this represents a real externally evaluated predicate, not an automatic guessed truth value. Arbitrary host acknowledgements do not modify predicates. F0 expressions use the bounded parser/evaluator described below; a supplied predicate never skips an unresolved F0.

Group return changes mode to outer at the same byte for source-established 8/A/B classes, non-E0 E-class boundaries, and listed outer F controls (F2/F3/F4/F5/F9/FA/FB/FE/FF). The outer decoder must then support that byte or stop. E0 random and unsupported group00/70 forms remain errors; they do not become fabricated group exits. Group flags4 are internal pending presentation flags; native commands in source-established operand ranges add flag2 only after acknowledgement, and an acknowledged message consumes its pending flags. This single-action interface does not batch messages into a source presentation-token array.

## Explicit host transactions

Messages, native commands/events, runtime/state writes, progress markers/redirects, external continuation5c requests and lifecycle completion become a stable `pending()` descriptor. It includes a monotonically increasing token, caller identifier, exact decoder instruction and message flags. No externally visible effect is performed by this class. The caller must perform the action and acknowledge the matching token with `succeeded=true`; failure or missing acknowledgement preserves the pending request and cursor for retry. Host effects must be retry-safe if the host reports failure after partial work. Source callbacks sometimes advanced eagerly; this facility deliberately commits only after acknowledgement.

Only progress redirects and external continuation requests accept/require an acknowledged in-slice offset. Other actions require no offset and advance to the source-defined following position. A redirect involving state5/yield requires the real host to complete its associated work before acknowledging; the machine does not infer it from a number. State5/state6/native payloads are requests, not implementations of those systems. State/progress writes require actual producer success. The host may validate a proposed acknowledgement before its own effects; invalid token/offset leaves machine state and pending action unchanged. Source lifecycle completion keeps its original cursor and marks finished only on successful acknowledgement.

`advance` after completion reports complete. Decode errors preserve the current instruction cursor; `decode_error()` explains the latest decode failure. `reset()` clears state/borrowing while retaining token serial to reject stale acknowledgements across restarts. Objects must not be copied while active (the caller must maintain a single owner); returned pending storage is read-only and valid until a mutating call. Callers must not fabricate C++ object aliases into source or response storage. The runner validates source/object ranges and acknowledgement/object overlap; it does not validate arbitrary dangling caller pointers.

No original story progression, generated command routing, complete predicate/native host implementation, random selector, message presentation, native event implementation, game-state owner, save compatibility or fully playable engine is claimed. Source-only delivery; no runtime, tests, game payloads or worker compilation. Lead owns batch integration/build.


## Bounded F0 integration

On F0 in either mode the machine parses from cursor+1 with its own fixed 256 nodes, 256 postfix-stack slots and 256 values. These are deliberately stricter capacities than the standalone decoder, not heap fallbacks. Only full parse and resolved evaluation success commit the predicate and parsed end offset. Parse/evaluation errors return expression_failure; expression_parse_result() preserves exact error/byte offset and expression_evaluation() exact error/node index. Missing provider/data returns predicate_required with unresolved evaluation and no F0 cursor advance or predicate change. Earlier successful steps in the same advance call remain committed.

bind_expression_provider installs an optional borrowed read-only provider/context; literal-only expressions require no provider. Providers must implement real requested data rather than invented defaults. Assignment/increment/decrement operations1–3 remain unsupported by the evaluator; E0 random remains unsupported. Rebinding while no host action is pending allows genuine missing data to be supplied and the same F0 retried. There is no execution of an unsupported expression as successful zero.

A busy guard rejects mutating machine methods during provider evaluation (reset becomes a no-op). The provider must never reenter advance, mutate machine/workspace/routes, free its context or modify provider-owned data during evaluation. The context object's full extent and any referenced objects must be disjoint from machine/routes/workspace; only its starting address can be checked by this opaque void-pointer API. This is a caller lifetime/alias contract, not general memory validation. The source slice and provider data must remain stable while parsing/evaluating. No runtime/tests were performed for this integration.
